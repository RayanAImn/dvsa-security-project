\section{Lesson 1: Event Injection}

\subsection*{Part 1) Goal and Vulnerability Summary}
This lesson demonstrates event injection in the DVSA order API path. The affected component is the API Gateway to Lambda request-processing workflow. A crafted payload can make backend code treat attacker-controlled content as executable behavior instead of plain data, which can lead to code execution in the lab Lambda context.

\subsection*{Part 2) Why This Works / Root Cause}
The root cause is unsafe deserialization or dynamic handling of user-controlled input. If the handler or one of its dependencies accepts serialized functions or evaluates request data as code, the Lambda runtime can execute unintended logic before normal validation completes.

\subsection*{Part 3) Environment and Setup}
\begin{itemize}
\item Region: \texttt{us-east-1}
\item Entry point: \texttt{/dvsa/order}
\item Backend path: order-processing Lambda workflow
\item Evidence sources: \texttt{vulnerabilities/lesson-01-event-injection/report-source.pdf}, CloudWatch log proof, and \texttt{redacted-requests.txt}
\end{itemize}

\subsection*{Part 4) Reproduction Steps}
\begin{enumerate}
\item Locate the API Gateway invoke URL used by the DVSA frontend.
\item Append the order path and send a crafted JSON payload containing the event-injection marker.
\item Observe the client response, which may be a generic internal error.
\item Open CloudWatch logs for the order Lambda.
\item Confirm that backend-side execution evidence appears in the logs.
\end{enumerate}

\subsection*{Part 5) Evidence and Proof}
\begin{itemize}
\item \texttt{vulnerabilities/lesson-01-event-injection/report-source.pdf} contains the imported evidence package.
\item \texttt{vulnerabilities/lesson-01-event-injection/redacted-requests.txt} stores the sanitized payload shape.
\item \texttt{screenshots/lesson-01/} stores endpoint discovery, exploit request, normal response, exploit evidence, and post-fix request screenshots.
\item CloudWatch is the primary proof source because API Gateway may hide backend execution behind a generic error.
\end{itemize}

\subsection*{Part 6) Fix Strategy / Probable Mitigation}
The fix belongs in the request parsing path. Remove unsafe deserialization, parse requests as strict JSON, and validate all fields against an allowlisted schema. User input must never be evaluated as code.

\subsection*{Part 7) Code / Config Changes}
\begin{itemize}
\item \texttt{fixes/lesson-01/before-code.txt}: vulnerable request-handling pattern
\item \texttt{fixes/lesson-01/after-code.txt}: safe parsing and validation pattern
\item \texttt{fixes/lesson-01/before-example.txt} and \texttt{after-example.txt}: behavior comparison
\item \texttt{fixes/lesson-01/explanation.md}: remediation explanation
\end{itemize}

\subsection*{Part 8) Verification After Fix}
Repeat the crafted payload. The fixed backend should reject it as invalid input, and CloudWatch should no longer show injected code execution. Normal order handling should still work with valid data.

\subsection*{Part 9) Structured Operation and Security Analysis}
\analysistables
{Lesson 01: Event Injection}
{Request data must remain data and must never execute inside the Lambda handler.}
{API payload, CloudWatch logs, source report PDF, and screenshot evidence.}
{Normal order requests follow the expected handler path and complete without injected behavior.}
{The crafted event causes backend execution evidence in CloudWatch.}
{The backend executed behavior derived from request data, which violates the intended separation between data and code.}
{Intentional misuse / security-relevant abuse}
{Safe JSON parsing and schema validation in the order request path.}
{The crafted payload is rejected and no backend execution evidence remains.}

\subsection*{Part 10) Takeaway / Lessons Learned}
Serverless functions still execute ordinary application code with cloud permissions. Unsafe parsing can turn a simple API request into backend code execution, so input must be treated strictly as data.

\section{Lesson 2: Broken Authentication}

\subsection*{Part 1) Goal and Vulnerability Summary}
This lesson demonstrates broken JWT authentication in the DVSA order workflow. The backend can trust a forged or modified token if it uses decoded claims without complete verification. The impact is user impersonation and unauthorized access to another user's order data.

\subsection*{Part 2) Why This Works / Root Cause}
JWT claims are visible to the client and can be edited. The weakness occurs when the backend uses identity fields such as \texttt{username} or \texttt{sub} without verifying the token signature, issuer, audience, expiry, and trusted subject.

\subsection*{Part 3) Environment and Setup}
\begin{itemize}
\item Region: \texttt{us-east-1}
\item Endpoint: DVSA order API
\item Users: one attacker account and one victim account in the lab
\item Tools: browser DevTools, decoded JWT inspection, and direct API testing
\item Evidence source: \texttt{vulnerabilities/lesson-02-broken-authentication/report-source.docx}
\end{itemize}

\subsection*{Part 4) Reproduction Steps}
\begin{enumerate}
\item Create or identify two lab users and place at least one order for each.
\item Capture a valid JWT from the attacker account through DevTools.
\item Inspect or decode the token to identify the identity claims.
\item Modify the forged token payload to use the victim identity claim.
\item Send the forged request to the order API.
\item Observe unauthorized access to the victim user's order data.
\end{enumerate}

\subsection*{Part 5) Evidence and Proof}
\begin{itemize}
\item \texttt{screenshots/lesson-02/from-report/} contains 8 extracted screenshots from the source report.
\item \texttt{vulnerabilities/lesson-02-broken-authentication/redacted-requests.txt} stores the sanitized request pattern.
\item The proof condition is that a forged token returns data belonging to another user.
\end{itemize}

\subsection*{Part 6) Fix Strategy / Probable Mitigation}
The fix belongs in the backend order-authentication path. The server must verify token integrity and trusted claims before using identity. Invalid signatures, wrong issuer or audience, expired tokens, and inconsistent subject claims must be rejected.

\subsection*{Part 7) Code / Config Changes}
\begin{itemize}
\item \texttt{fixes/lesson-02/before-order-manager.js}: vulnerable pattern that trusts decoded claims
\item \texttt{fixes/lesson-02/after-order-manager.js}: verified JWT pattern using trusted claims
\item \texttt{fixes/lesson-02/explanation.md}: remediation explanation
\end{itemize}

\subsection*{Part 8) Verification After Fix}
Repeat the forged-token request. It should be rejected, while a valid user token should still return only that user's own orders.

\subsection*{Part 9) Structured Operation and Security Analysis}
\analysistables
{Lesson 02: Broken Authentication}
{Only verified identity claims may authorize order access.}
{Browser workflow, JWT payload inspection, API request and response evidence, and source-report screenshots.}
{A valid user token returns only that user's own order data.}
{A forged token returns another user's order data.}
{Caller-controlled claims were treated as proof of identity even though they were not cryptographically verified.}
{Intentional misuse / security-relevant abuse}
{JWT signature and claim verification in the backend order-access path.}
{Forged tokens are rejected and valid tokens still return only the caller's own data.}

\subsection*{Part 10) Takeaway / Lessons Learned}
Decoding a JWT is not authentication. The backend must verify the token before trusting any claim.

\section{Lesson 3: Sensitive Data Exposure}

\subsection*{Part 1) Goal and Vulnerability Summary}
This lesson shows that DVSA receipt or storage workflows can expose private data through API responses, generated files, logs, or object access. The main impact is disclosure of user receipt or order-related information outside the intended ownership boundary.

\subsection*{Part 2) Why This Works / Root Cause}
The root cause is weak authorization and weak data minimization around receipt-related data. If the backend exposes receipt content or access links without checking ownership, users can access information outside their intended boundary.

\subsection*{Part 3) Environment and Setup}
\begin{itemize}
\item Region: \texttt{us-east-1}
\item Services: API Gateway, Lambda, DynamoDB, S3 receipts, and CloudWatch
\item Evidence source: \texttt{vulnerabilities/lesson-03-sensitive-data-exposure/report-source.pdf}
\item Supporting artifacts: redacted request samples and screenshot evidence
\end{itemize}

\subsection*{Part 4) Reproduction Steps}
\begin{enumerate}
\item Create normal receipt or order data in the lab.
\item Trigger the vulnerable receipt path or API response path.
\item Capture the exposed response, file, or object evidence.
\item Confirm that the accessed data should belong only to the owner.
\item Redact identifiers before storing the proof.
\end{enumerate}

\subsection*{Part 5) Evidence and Proof}
\begin{itemize}
\item \texttt{screenshots/lesson-03/} contains endpoint discovery, token capture, DynamoDB evidence, sensitive file evidence, exploit evidence, and post-fix results.
\item \texttt{vulnerabilities/lesson-03-sensitive-data-exposure/redacted-requests.txt} stores the sanitized request or response sample.
\item The exploit is proven when receipt data or receipt access becomes available without proper ownership checks.
\end{itemize}

\subsection*{Part 6) Fix Strategy / Probable Mitigation}
Add ownership checks before returning receipt data or signed URLs. Keep receipt objects private, generate short-lived access only after authorization, and avoid returning unnecessary sensitive fields.

\subsection*{Part 7) Code / Config Changes}
\begin{itemize}
\item \texttt{fixes/lesson-03/before-code.txt} and \texttt{after-code.txt}: pre-fix and post-fix behavior
\item \texttt{fixes/lesson-03/before-example.txt} and \texttt{after-example.txt}: evidence-oriented comparison
\item \texttt{fixes/lesson-03/explanation.md}: remediation explanation
\end{itemize}

\subsection*{Part 8) Verification After Fix}
Repeat the receipt access attempt as an unauthorized user. The response should be denied or sanitized, while the legitimate owner can still access the correct receipt data.

\subsection*{Part 9) Structured Operation and Security Analysis}
\analysistables
{Lesson 03: Sensitive Data Exposure}
{Users may access only their own receipt data and only the minimum required fields should leave the backend.}
{API responses, receipt objects, source report PDF, screenshots, and redacted request patterns.}
{Authorized owner access returns the expected receipt information only.}
{Private receipt data or links become visible outside the ownership boundary.}
{Private data crossed the authorization boundary because the backend exposed more than it should.}
{Intentional misuse / security-relevant abuse}
{Ownership checks and private receipt access controls in the receipt retrieval path.}
{Unauthorized access is denied or sanitized, while owner access still works.}

\subsection*{Part 10) Takeaway / Lessons Learned}
Sensitive data controls must be enforced where data leaves the backend, not only where it is stored.

\section{Lesson 4: Insecure Cloud Configuration}

\subsection*{Part 1) Goal and Vulnerability Summary}
This lesson demonstrates that insecure S3 configuration can allow untrusted files into the DVSA receipt-processing workflow. The affected component is the receipts bucket and its trust relationship with downstream Lambda processing. The impact is that a storage misconfiguration becomes a backend attack path.

\subsection*{Part 2) Why This Works / Root Cause}
The root cause is weak S3 public-access or bucket-policy configuration combined with Lambda processing that trusts bucket contents. If unauthorized users can place objects where Lambda expects application-generated receipts, the backend processes untrusted input.

\subsection*{Part 3) Environment and Setup}
\begin{itemize}
\item Region: \texttt{us-east-1}
\item AWS services: S3 bucket, Lambda receipt-processing path, AWS Console or CLI
\item Evidence source: \texttt{vulnerabilities/lesson-04-insecure-cloud-configuration/report-source.docx}
\item Supporting artifact: \texttt{redacted-requests.txt}
\end{itemize}

\subsection*{Part 4) Reproduction Steps}
\begin{enumerate}
\item Inspect the receipt bucket permissions and public-access settings.
\item Attempt a controlled upload of a receipt-like object from outside the intended trust boundary.
\item Observe whether backend processing accepts or reacts to the object.
\item Capture S3 and Lambda evidence from the lab environment.
\end{enumerate}

\subsection*{Part 5) Evidence and Proof}
\begin{itemize}
\item \texttt{screenshots/lesson-04/from-report/} contains 12 extracted screenshots from the source report.
\item \texttt{vulnerabilities/lesson-04-insecure-cloud-configuration/redacted-requests.txt} stores the sanitized CLI pattern.
\item The exploit is proven when unauthorized upload or access reaches the trusted receipt-processing path.
\end{itemize}

\subsection*{Part 6) Fix Strategy / Probable Mitigation}
Enable S3 Block Public Access, restrict bucket policy and ACLs, validate object keys and file types, and allow only trusted application roles to write objects that trigger Lambda processing.

\subsection*{Part 7) Code / Config Changes}
\begin{itemize}
\item \texttt{fixes/lesson-04/before-example.txt}: permissive pre-fix state
\item \texttt{fixes/lesson-04/after-example.txt}: tightened bucket and workflow controls
\item \texttt{fixes/lesson-04/explanation.md}: remediation explanation
\end{itemize}

\subsection*{Part 8) Verification After Fix}
Repeat unauthorized upload or access attempts. They should fail, while the legitimate receipt workflow continues to work.

\subsection*{Part 9) Structured Operation and Security Analysis}
\analysistables
{Lesson 04: Insecure Cloud Configuration}
{Only trusted roles and workflows may write receipt objects that the backend processes.}
{S3 configuration evidence, source report screenshots, CLI patterns, and Lambda workflow context.}
{Legitimate receipt objects are created and processed only by the intended application workflow.}
{The bucket accepts input or access beyond the intended trust boundary.}
{A cloud resource granted more access than the application trust model intended.}
{Accidental misconfiguration}
{S3 Block Public Access and restricted bucket policy in the receipt bucket configuration.}
{Unauthorized write and access attempts fail while legitimate receipt handling remains functional.}

\subsection*{Part 10) Takeaway / Lessons Learned}
Cloud configuration is part of application security. A storage misconfiguration can become a backend exploit path when downstream services trust stored content.

\section{Lesson 6: Denial of Service}

\subsection*{Part 1) Goal and Vulnerability Summary}
This lesson demonstrates a denial-of-service condition in the DVSA billing workflow. The affected path is the \texttt{/dvsa/order} billing action, which reaches the \texttt{DVSA-ORDER-BILLING} Lambda function. Repeated billing requests can consume backend processing capacity and reduce availability for legitimate users.

\subsection*{Part 2) Why This Works / Root Cause}
The vulnerable design does not sufficiently limit repeated or concurrent billing requests at the API edge. The billing path performs backend work for each request and depends on limited Lambda and API Gateway capacity. Without throttling, idempotency, or per-user controls, a small burst of duplicate requests can degrade the backend.

\subsection*{Part 3) Environment and Setup}
\begin{itemize}
\item Region: \texttt{us-east-1}
\item API endpoint: \texttt{https://<api-id>.execute-api.us-east-1.amazonaws.com/dvsa/order}
\item Action: \texttt{billing}
\item Backend function: \texttt{DVSA-ORDER-BILLING}
\item Evidence sources: browser workflow, PowerShell or curl output, CloudWatch logs, Lambda metrics, and API Gateway throttling settings
\end{itemize}

\subsection*{Part 4) Reproduction Steps}
\begin{enumerate}
\item Confirm the normal billing and order workflow works from the DVSA frontend.
\item Capture the billing request from browser DevTools.
\item Send one baseline billing request with the captured request body and a redacted Authorization header.
\item Run a controlled repeated-request test with a small serialized count.
\item Run a controlled parallel-job test against the same lab endpoint.
\item Compare returned status codes and response bodies.
\item Open CloudWatch and Lambda metrics for \texttt{DVSA-ORDER-BILLING} to confirm backend impact.
\end{enumerate}

\subsection*{Part 5) Evidence and Proof}
\begin{itemize}
\item \texttt{screenshots/lesson-06/} contains screenshots for normal workflow, captured request details, repeated-request output, Lambda metrics, CloudWatch logs, and API Gateway throttling.
\item The controlled parallel test produced mixed \texttt{200}, \texttt{500}, and \texttt{502} responses.
\item Mixed backend failures during a small parallel burst show that duplicate billing requests can degrade availability.
\end{itemize}

\subsection*{Part 6) Fix Strategy / Probable Mitigation}
The fix belongs at both the API Gateway and backend workflow layers. API Gateway should enforce throttling so small bursts do not reach Lambda unchecked. The billing function should also be made idempotent per order and user so duplicate billing attempts are rejected cheaply and consistently.

\subsection*{Part 7) Code / Config Changes}
\begin{itemize}
\item \texttt{fixes/lesson-06/before-example.txt}: pre-fix repeated-request behavior
\item \texttt{fixes/lesson-06/after-example.txt}: post-fix throttling and idempotency behavior
\item \texttt{fixes/lesson-06/explanation.md}: mitigation summary
\end{itemize}

\subsection*{Part 8) Verification After Fix}
Repeat the same controlled test after throttling and idempotency controls are applied. Excess requests should be throttled or rejected cleanly instead of causing backend instability. The normal checkout workflow should still work for legitimate users.

\subsection*{Part 9) Structured Operation and Security Analysis}
\analysistables
{Lesson 06: Denial of Service}
{Billing requests should be processed fairly, and duplicate or concurrent bursts should not exhaust backend capacity.}
{Browser flow, captured API request, PowerShell output, CloudWatch logs, Lambda metrics, and API Gateway throttling settings.}

\subsection*{Part 10) Takeaway / Lessons Learned}
Availability is a security property. Critical serverless workflows need throttling, idempotency, and graceful failure under burst conditions.

\section{Lesson 7: Over-Privileged Function}

\subsection*{Part 1) Goal and Vulnerability Summary}
This lesson demonstrates an over-privileged Lambda execution role. The affected function is \texttt{DVSA-SEND-RECEIPT-EMAIL}, whose role originally included permissions broader than the receipt-email workflow requires. The impact is increased blast radius because any code running inside the function inherits the role's temporary credentials.

\subsection*{Part 2) Why This Works / Root Cause}
Lambda functions run with execution-role credentials provided by AWS. If a function role allows broad access, a compromised or abused function can perform every action allowed by that role, even when those actions are unrelated to the function's intended purpose. The root cause is failure to apply least privilege.

\subsection*{Part 3) Environment and Setup}
\begin{itemize}
\item Region: \texttt{us-east-1}
\item Function: \texttt{DVSA-SEND-RECEIPT-EMAIL}
\item Services involved: Lambda, IAM, SES, S3, DynamoDB, CloudWatch, and IAM Policy Simulator
\item Supporting evidence: screenshots and redacted IAM policy examples
\end{itemize}

\subsection*{Part 4) Reproduction Steps}
\begin{enumerate}
\item Open AWS Lambda and locate \texttt{DVSA-SEND-RECEIPT-EMAIL}.
\item Open the function permissions tab and follow the execution-role link.
\item Review attached policies for broad actions such as \texttt{ses:*} or wildcard resources.
\item Open IAM Policy Simulator and test representative SES, S3, and DynamoDB actions.
\item Record which actions are allowed before the fix.
\item Replace the broad policy with a least-privilege policy.
\item Re-run the simulator and confirm unnecessary actions are denied.
\item Run the normal DVSA order workflow to confirm legitimate receipt behavior still works.
\end{enumerate}

\subsection*{Part 5) Evidence and Proof}
\begin{itemize}
\item \texttt{screenshots/lesson-07/} contains Lambda page, execution-role page, broad SES evidence, simulator checks, post-fix simulation, and normal workflow screenshots.
\item \texttt{diagrams/lesson-07-blast-radius.png} shows the blast-radius analysis.
\item \texttt{fixes/lesson-07/before-policy.json} and \texttt{after-policy.json} provide the policy comparison.
\end{itemize}

\subsection*{Part 6) Fix Strategy / Probable Mitigation}
The fix belongs in the Lambda execution role. Broad managed policies and wildcard-resource permissions should be removed. The replacement policy should allow only the actions required for the receipt workflow, together with minimum CloudWatch logging permissions.

\subsection*{Part 7) Code / Config Changes}
\begin{itemize}
\item \texttt{fixes/lesson-07/before-policy.json}: broad pre-fix IAM policy
\item \texttt{fixes/lesson-07/after-policy.json}: least-privilege target policy
\item \texttt{fixes/lesson-07/explanation.md}: remediation and verification notes
\end{itemize}

\subsection*{Part 8) Verification After Fix}
After applying the least-privilege policy, re-run IAM Policy Simulator checks for unnecessary SES, S3, and DynamoDB actions. Broad or unrelated actions should be denied, and the normal order and receipt workflow should still work.

\subsection*{Part 9) Structured Operation and Security Analysis}
\analysistables
{Lesson 07: Over-Privileged Function}
{The receipt-email function should have only the permissions required to send receipts and write logs.}
{Lambda permissions page, IAM role policies, IAM Policy Simulator, screenshot evidence, and the blast-radius diagram.}
{Normal order and receipt workflow still works after the IAM fix.}
{Broad SES and unrelated service access were allowed before the fix.}
{The role allowed actions broader than the function required, increasing blast radius if the function was abused.}
{Accidental misconfiguration}
{Least-privilege IAM policy on the \texttt{DVSA-SEND-RECEIPT-EMAIL} execution role.}
{IAM Policy Simulator denies unrelated actions and the normal workflow still works.}

\subsection*{Part 10) Takeaway / Lessons Learned}
In serverless systems, the function role is a security boundary. Least privilege reduces blast radius so one function issue does not become broad access to unrelated AWS services.
